## 始め方

```sh
npm install          # terser 5.36.0 と playwright 1.56.1（ブラウザは /opt/pw-browsers にある）
npm test             # ビルドしてから Playwright のテスト 110 件（paint.test.mjs 90 件・audit.test.mjs 10 件・memory.test.mjs 10 件）
npm run bench        # 性能計測（メインスレッドの占有時間）
npm run pop          # 蛍光ペンの先端の消える画素（ぴょこぴょこ）と、1〜2 フレーム後のペン先との隙間（T-055）
npm run predict -- <paint-input-*.json>  # 録った入力（T-070）で、予測の方法ごとの 1 フレーム後のペン先とのずれ・はみ出し・消える長さを比べる（T-060）。負荷の様子（フレームの間隔・届くまでの遅れ・予測線の点滅）も出す（T-087）
```

- ソースを変えたら `npm run build` を流し、`dist/` と `docs/` もコミットする。CI は生成物がソースと一致するかを `git diff --exit-code -- dist docs` で確かめる。
- Artifact の更新は、`node build.mjs --page <scratchpad>/paint-bookmarklet.html` で本文だけの版を作って公開する。別のセッションから更新するときは、先に URL を read してから url を指定して publish する。

- 拡大（ピンチ）の基準（T-136）: client 座標・live / pred・ツールバーはレイアウトの画面（layout viewport）が基準。面の位置（origin・sizeSurface の hdx・画面に固定の fx）は scrollX ではなく lvX / lvY（visualViewport の pageLeft − offsetLeft。Chrome では scrollX と同じ）で読み、live / pred の大きさと layBar の幅は lvW / lvH（innerWidth と wrap の大きさの大きい方）。scrollX / scrollY を読むのは、scrollTo で動かす処理（2 本指・慣性・offTop）だけ。2 本指の指の位置は vpX / vpY（client − offsetLeft）。iPhone の WebKit では scrollX・innerWidth が見えている範囲（visual viewport）の物らしい（未確認）。拡大した iPhone（IOS で VV.scale > 1.01）では、描いている途中の線（.g）を面（sroot）に移して translate(sox / sdpr, soy / sdpr) に置く（placeLive。T-138。画面に固定した層がずれて見えたため）。live / pred に描く物は、どちらの層でも V のまま（確定は S = V × sk + sox で同じ）。.g を動かすのは押したとき（live が空のとき）だけ
- 座標は 2 種類。V は画面のデバイスピクセル（client × dpr。入力、live / pred）、S は面のピクセル。S = V × sk + (sox, soy)。sk・sox・soy は onDown の `mapNow()` で 1 回だけ求め、ストローク中は変えない。スクロール位置は必ず `origin()` を通して読む（画面に固定の間は入れた時の fx / fy を返す）。押していない間（ホバーなど）に sox / soy を使うときは、先に mapNow() を呼ぶ（最後に押してからスクロールしているかもしれない。T-048）。面の密度 `sdpr` は起動時の dpr で固定し、表示タイルの大きさ DT もそこで決まる。
- 面を変える操作は必ず `push(R, atlas, b)` で履歴に積む（全消去だけは atlas が null で、タイルを手の d に移す。T-112。R は S 座標、b は描いた物の外接矩形で、選択ツールのクリックで使う。消しゴム・全消去・選択の削除は b なし）。R の矩形は重なってもよいが、アトラスの画素はどの矩形も同じ時点（その手の前）の状態にそろえる。面に描くのは必ず R の中だけ（R の外に描いた画素は元に戻しても残る。T-044 で塗りつぶしの 1px の膨張が画面の外へはみ出していた）。描いた範囲 `cb*` は push / swap で広げ、clearAll で空にする。塗りつぶしの読み戻し範囲と全消去が積むタイルがこれに依存している（画素は cb* の中にしかない）。全消去は、直前の手が全消去（履歴の手の `clr`）か、cb* が空で文字もなければ何もしない（T-058）。直前の手が描く手（b がある）でなく文字もなければ、hasInk で cb* に掛かるタイルを読み戻し、画素がなければ何もしない（T-063。消しゴム・選択の削除・最初まで元に戻した後）。b は描く手（線・図形・塗りつぶし・選択の移動）にだけ付ける決まりなので、新しい手を足すときも守る。
- 消しゴムでは `markBox` / `markSeg` を `erasePts()` より前に呼ぶ（削る前のタイルを退避するため）。
- 履歴の手の画素は、canvas（h.c、全消去はタイルの t.c）か、縮めた形（z と zw・zh。canvas は大きさ 0 にして持ったまま）のどちらか（T-114）。履歴の画素を使う所は、先に z を戻す（swap は unz、swapTiles はタイルの unz、toAtlas は unzIm）。新しく履歴の canvas を読む・入れ替える処理を足すときも同じにする。縮めるのは hpos の前後 ZHOT 手の外だけで、描いている間・2 本指のスクロールと慣性の間はしない。スマホ（MEM）で履歴が上限の半分を超えたときだけ縮める（T-120）。縮めた手の pix は z の語数。zJob は、途中で入れ替えた・捨てた（o.c が変わる・大きさ 0・d から外れる）らやめる。読み出しは帯ごとに別の canvas に写してから（同じ canvas を 2 回以上 getImageData すると、Chrome がページのコンソールに警告を出す）。
- スマホ・タブレット（MEM が 0 でない）の canvas の合計（canvasPix ＋ hpix）は MEM（192 MB）を目安に抑える（T-113）。trim が古い手から捨て、絵そのもの（面のタイル）は捨てない。履歴は少なくとも画面 1 枚分（W × H）残す。長く残る canvas を新しく持つ物を足すときは canvasPix に数え、履歴の手の pix は手が実際に持っている画素に合わせる（swapTiles は戻したタイルの分を引き、toAtlas はアトラスの分にする。全消去はタイルを面から外してから push する。二重に数えると、要らない古い手まで捨てる）。trim が捨てるのは hpos より前の手だけ（やり直しの並びを崩さない）。
- 文字の物は面の要素（.to）で、状態は [文字, x, y, 大きさ, 色, 濃さ]（S の px、CSS px の整数に丸める）。状態を変えるのは必ず `tApply(物, 状態)`（null で外す）で、その前の状態を履歴の手の `t` に [物, 前の状態] として積む。undo / redo は `swapAll` が画素（c があれば swap）と文字（t があれば swapText）を両方入れ替える。
- インストールページで選んだ既定は、コードの中の文字列 `'__PAINT_DEFAULTS__'` を JSON の文字列に置き換えて渡す（`DEF`）。terser は JSON.parse の引数を畳まないので、この文字列は圧縮後もそのまま残る（変えるときは dist で確かめる）。
- 設定は「組み込み → DEF（インストールページ）→ サイトの保存」の順に重ねる。サイトに書くのは、組み込み＋DEF からの差分だけ（`base` と比べる）。保存は remember() から 400 ms 後にまとめて行い、hide の前には待たずに済ませる。起動中（`ready` が立つ前）の setColor などは保存しない。
- 入力中の文字（`ta`）と浮いている選択（`sel`）は、面や履歴を変える操作の前に `settle()`（commitText + dropSel）で確定する（undo・redo・clearAll・exportBlob・togglePass・hide。onDown と setTool は道具に応じて片方だけ）。新しく面を変える操作を足すときも同じにする。選択が浮いている間は、元の範囲が面から消えていて履歴とずれている。文字の入力欄のイベント（TA_STOP）はページへ渡さない。
- 入力のホットパス（onMove 以下）では、オブジェクトの割り当ても DOM の読み書きもしない（例外は開発用の入力の録画を入れている間だけ。録っていなければ recCur の比較 1 回）。面のタイルの読み戻しもしない。`now()` を呼ぶのは HUD を表示しているときだけ。erasePts は `ePts`（Float64Array）と既存タイルのループだけで動く。自前の予測（ownPred）も輪（hT / hX / hY、HN = 64）と px / py / pt だけで動く。`lt` は最後に動いた点の時刻（筆の速さ・速度のならし・予測線を消す PRED_TTL が使う）。止まっている点は hPush だけして lt を進めない（進めると、整数座標でゆっくり動かしたとき筆の速さが跳ねる）。hPush は前のフレームから最初に来た点の時刻を fT に残し、tick が届くまでの遅れ dl に使う（onDown で fT = 0 に戻す。戻さないと前の線の時刻から測って dl が何秒にもなる）。hPush は点の間隔 pdt（50 ms 未満の間隔を 10% ずつならす。線をまたいで持ち越す）も測り、tick が止まったとみなすまでの待ち G = 3 × pdt（10〜40 ms）に使う（T-115）。
- ペン・蛍光ペンの onMove は、新しい点が 1 つもない入力（rawupdate で描き終えた点の pointermove。hN が増えない）では predict と drawTail を呼ばない（T-112）。描くと pred の canvas の書き出し（desynchronized の DispatchFrame）が 1 回増え、メインスレッドの大半はこの書き出しだった（監査: 125 Hz で入力 1 件あたり約 2.5 回 → 2 回）。ブラウザの予測（ppred = 'chrome'）と蛍光ペンの必要な分だけ（sNeed）は pointermove で新しくなるので描く。Ink Trail の updateInkTrailStartPoint はいつも呼ぶ。
- 文字の入力欄 ta・薄い答え ghostEl・測る用の mta は、wrap の中でツールバーより前に置く（bar.before。T-092）。どれも z-index なしの absolute なので、後ろに足すと開いたパネルより手前に描かれる。wrap に新しく重ねる物を足すときも、ツールバーより手前に出したい物（お知らせ・一覧・HUD）以外は bar.before にする。
- ツールバーとその他に並べるのは layout() だけ（T-088）。ボタンや項目を足すときは、本家と Simple のどちらに出すかを決めて layout の並び（本家のその他は mainMore）に入れる。Simple の決まり（お知らせ・ペンの値の預かり・2 本指など）は HANDOFF-simple.md の不変条件。
- ツールバーを組み直す（layBar。.two の付け外しと幅）のは、幅（innerWidth）が変わったときと版を切り替えたときだけ（T-134。lbW に最後の幅を覚える。LINE などでは、スクロールでブラウザのバーが縮むたびに高さだけが変わり、そのたびに class と幅を外して付け直していた。iPhone ではガラスの層が作り直されて透明に見えていたらしい）。fit で毎回ツールバーの class・style を書き換える処理を足さない（moveBar の transform は同じ値なら書き換わらない）。
- live / pred の W / H は、大きくなるときはすぐ作り直し、縮むのは面積が 4 分の 3 未満になってから 1 秒後（fit(true)。描いている間は pendingFit で待つ。T-113）。引いて大きさを変えている間に何度も作り直さないため、すぐには縮めない。面は `sizeSurface()` で文書の大きさに合わせる（縮むこともある。タイルは消さず、clip で隠れるだけ）。
- 描画中（`act !== -1`）は fit・undo・clear をしない。fit は `pendingFit` で後回しにする。
- 確定の受け渡し: commitLive はタイルに描いたのと同じフレームでグループの opacity を 0 にし、live は 2 フレーム後に `finishHandoff()` で消す。.g（とお知らせの .t）には will-change: opacity を付けておく（T-119。付けないと opacity を変えるたびに Chrome がページ全体を Paint し直し、6000 要素のページで 1 本 約 16 ms かかっていた。付ければ合成だけで済み、合成のパスの数も変わらない）。次の onDown・undo・redo・fit は先に finishHandoff を呼ぶ。受け渡し中は liveAlpha が opacity を戻さない。
- 半透明の線（T-056、blend が既定の 'canvas'）: ペン・蛍光ペンは live に線の濃さで描く。鉛筆は濃さ 100% でもこの描き方（sTr）にする（T-122。かすれの模様は半透明の画素なので、ふつうに重ねると入力ごとのつなぎ目の丸い先端が濃くなる）。抜く（destination-out）ときだけ strokeStyle を不透明の #000 にする（模様のままでは半透明の画素の所が抜き切れない。cutPred も #000）。足すときの濃さは sKA（'canvas' なら sA、'group' なら 1。'group' では .g の opacity が濃さを付ける）。stk() が、新しい部分の所を destination-out で抜いてから lighter・globalAlpha = sA で足す（濃さ = sA ×（今までの形 ∪ 新しい部分）。不透明で重ねてから濃さをかけるのと同じ計算）。pred は globalAlpha = sA で描き、drawTail の最後に cutPred が、描いた部分の形（addPiece で覚えた区間。輪 RN = 16384 個、RB = 32 個ずつの外接矩形で絞る）を destination-out で抜く（live と重ねても、縁のぼかしの数画素を除いて sA を超えない。live は区間ごとの確率的な和、抜く形は 1 回の stroke の幾何的な和なので、縁だけ少し抜き足りない）。図形は live に直接 sA で描く（毎回描き直すので重ならない）。確定は live をそのまま（sCa = 1）面に合成する（前の方式と 8 ビットの丸めで 3 以内）。まとめた要素（.g）の opacity は 1 のまま（確定の受け渡しで 0 にするのは同じ）。前の方式（'group'）では live / pred に不透明で描いて .g に opacity をかけ、liveAlpha が押す前に合わせておく（描き始めの 1 フレームが濃くならないように）。どちらの方式も壊さない。描いている途中にキャンバスからキャンバスへ drawImage しない（コピー元を描き換えると、スナップショットの分だけキャンバス全体のコピーが走る）。unbounded な合成（destination-in・source-in・copy など）も canvas 全体に効くので、入力のたびには使わない。
- scroll / wheel のリスナーは登録しない（テストで確かめている）。スクロールはブラウザに任せる（2 本指と慣性だけは、pointer の動きから scrollTo する）。
- 2 本指のリスナー（TWO）は pad に capture で登録する。bubble で足すと onDown の後に呼ばれ、1 本目の線が描き始まってしまう。2 本目が来たら、1 本目で始めた手（線・図形・消しゴム・選択）は abortStroke で取り消し、tapId も消す。ただしペン・蛍光ペンの線を押してから KEEP_MS（150 ms）以上たち、線の外接矩形（x0〜x1・y0〜y1）が KEEP_PX（16 CSS px）以上なら endStroke で確定して残す（T-109）。慣性で滑っている間の押下は止めるだけで、その指は離すまで描かない（scr = 2）。ただし慣性の速さが KSTOP（0.3 px/ms）未満なら、止めてその指で描く（T-121）。スクロールの間の 3 本目以降の指も描かない。ペンで描いている間と、ペンを離した・近づけてから 500 ms のタッチ（手のひら）はスクロールにも使わず、ペンやマウスで押したら 2 本指のスクロールはそこで止める（T-112。onDown のパームリジェクションと同じ決まり）。慣性の rAF は hide で止める（destroy も hide を通る）。押した瞬間に面を変える道具をタッチに足すときは、塗りつぶし・文字と同じく離したとき（tapId）にする（押した瞬間だと 2 本指でスクロールするたびに実行される）。
- 線の終わり（pointerup・pointercancel・lostpointercapture）が pad に届かないと、act が -1 に戻らず、onDown・undo・redo・clearAll が全部黙って返る（T-118 の前は、hide するまで止まったままだった）。wrap の capture の pointerdown で、同じ種類（aType）の primary の押下が来たら endStroke で確定して戻す（前の指・ペン・マウスはもう離れている。2 本目の指は primary でない）。onDown より先に呼ばれるので、ツールバーのタップでも戻る。act !== -1 で返す処理を足すときは、この戻り方を前提にする。
- パネルは同時に 1 つだけ。閉じるのは wrap の pointerdown（capture）・Esc・hide。capture のリスナーはパネルが開いていなければ比較 1 回で戻る。パネルはバーの子（absolute）なので、バーの幅（measureBar）には入らない。
- innerHTML・style 属性・外部リソースは使わない（CSP と Trusted Types への対策）。
- 2 回目の実行は表示の切り替えだけ（`window.__paintBookmarklet` で判定）。閉じた後の取り消し待ち（`byeT`）の間は、show / toggle が reopen になる。Esc と「−」は hideHint で隠し、HINT_MS（4 秒）の間「ブックマークレットで再表示」を出す（`hintT`。close の取り消し待ちと同じく、お知らせ以外は消えて入力のリスナーも外れている）。show・close・destroy は先に endHint を呼ぶ。ブックマークレットと API の hide はお知らせを出さない。
- × は `close()`（描いた物があれば BYE_MS = 8 秒の取り消し待ち。その後に destroy）。API の `destroy()` はすぐに解放する（テストで確かめている）。取り消し待ちの間は visible = false で、入力のリスナーも外れている。

## 決定事項と理由

- 絵はページに貼り付ける（T-003、ideas/scroll-follow.md の方式 B）。確定した絵はページ座標の canvas タイル（面）に描き、スクロールはブラウザの合成に任せる。ページ全体の大きさのキャンバス 1 枚（方式 A）は長いページでメモリと上限に当たり、スクロールのたびに JS で動かす方式（C）は絵が 1 フレーム以上遅れるので捨てた。
- 画面に固定（T-016、ユーザーが作ると決め、その他のメニューに置いた）: 入れると、面をその時のスクロール位置（fx, fy）のまま position: fixed（left = hdx − fx）にする。スクロールで JS が動かないのは同じ。切るときは、今見えている位置のままページに付け直す: スクロールした分 Δ を S にして shiftAll で面のタイルを描き直し（切る時だけ描いた量に比例する）、履歴の矩形・外接矩形・文字の状態をずらす。文字は CSS px の整数のままずらす（sdpr が整数でないと、線との差が 1 デバイス px 未満出ることがある）。文書の上や左にはみ出した所は消える。固定の間は hdx を測らない。固定にする前のページの位置へ戻す案（切ると絵が飛ぶ）と、面の原点をずらし続ける案（文書の上端側に描けない所ができる）は捨てた。サイトごとには覚えない。
- 描いている途中の線（live / pred）は画面に固定のまま。入力の経路と遅延を一切変えないため。代わりに描画中のスクロールには追従しない（開始時の位置に確定）。
- 表示タイルは約 256 CSS px（DT = 128 × max(2, round(sdpr × 2)) デバイス px）。512 px だと初めて触れたときの確保が @2x で重く、128 px だと要素数が増える。履歴タイル 128 の倍数なので、履歴タイルが表示タイルをまたがない。
- 表示タイルは desynchronized にしない。数が多いと低遅延の経路が重く、合成の順序も live とずれる。ちらつきは受け渡し（2 フレーム後に live を消す）で防ぐ。
- 面の密度は起動時の dpr で固定する。表示倍率を変えても絵を作り直さず、sk で座標を換算する（ブラウザが拡大縮小して表示する）。
- 面は documentElement 直下の absolute 配置で、html のずれ（margin・border・position）は getBoundingClientRect から求めた hdx / hdy で打ち消す。contain: strict と overflow: clip で、はみ出してスクロール範囲を広げない。
- 範囲外にしたもの: ページ内の一部だけがスクロールする要素（Gmail など。T-017 の候補）、描いた後に本文が動くことによるずれ。

- 履歴の圧縮（T-114、ユーザーの提案: 最新のから解凍できるなら速度に支障はあまりなさそう。または一部だけ。R-014 で「おすすめの一部だけ」に決まった）: 元に戻す・やり直すの近く（前後 4 手）は canvas のまま、遠い手だけを 1 秒何もしなかったときに縮める。形は自前のラン長（同じ画素が 3 つ以上続く所を [個数, 画素] に）で、戻すのが同期なので元に戻すに待ちがない。ブラウザの deflate（CompressionStream）は 25〜300 分の 1 まで縮むが非同期で、元に戻すが待ちになるので採らなかった。測った縮み方は、2x のスマホ 1 画面で手書き 3 行 27 分の 1・9 行 9 分の 1・鉛筆 6 分の 1、塗りつぶしの前の一様な画面はほぼ 0。半分より縮まない物は canvas のまま（nz）。読み出しと書き戻し（getImageData → putImageData）は、Chrome ではソフトウェアと GPU の両方で、半透明の画素を含めて変わらなかった（全部の濃さと値の組で確かめた）。WebKit は未確認なので、zProbe で半透明の往復と不透明の画素の揺らぎを確かめ、だめなら縮めない（Safari のプライベートの指紋対策や Brave は、読み出しに ±1〜3 の揺らぎを足す）。1 回で大きな canvas を読むと、全画面の塗りつぶしの手で 1 回 8〜76 ms（ヘッドレス）ふさいだので、約 1 MB の帯に分けて 30 ms おきに読む（1 帯 2〜8 ms）。縮めた手まで元に戻すのは 5〜25 ms（前は 1 ms 前後）。
- 線の終わりを取りこぼしたときの戻し方（T-118、ユーザーの報告: 書いたあと、すぐ全消しを使っても効かない。Claude アプリの中のブラウザ・本家・2 回目で消える）: ヘッドレスでは、指を離した合図を届けない合成の線で同じ症状（全消去・元に戻す・次の線が効かない、線は live に残る）を再現した。iPhone で合図が来ない理由は WebKit のソースからの推測（WKTouchEventsGestureRecognizer の reset は明示の取り消しのときだけ Cancel を送る。アプリ・OS のなぞる操作が指を取ると pointerup も pointercancel も来ない。未確認）。戻すときは取り消さずに確定する（見えていた線なので）。押したときに戻すだけで、時間で戻す案は採らなかった（止まっているのか、指を置いたまま動かしていないのか区別できない）。2 回目で効いた理由は未確認（WebKit が後から lostpointercapture を出したのかもしれない）。
- 描き心地を最優先にした監査（T-117、ユーザーの依頼: やっぱり一旦、描きごこちを最優先して、全体を調べてきて）: T-111 と同じくサブエージェント 3 つ（不具合と状態の流れ・遅れと重さ・線の形と iPhone の入力）に分けた。T-113〜T-116 のうち入力のたびの処理を重くした物はなく（rawupdate 1 件 約 0.05 ms・pointermove 約 0.1 ms、canvas の書き出しも T-112 と同じ）、描くそばに仕事を足したのは T-114 の履歴の圧縮だけだった。見つかった物は TASKS.md の候補 T-119〜T-129 にした。確かめて問題がなかった物: 確定した線は描いている間の線と画素単位で同じ（3x）、半透明の重なりに継ぎ目なし、24 通り × 60 手のでたらめな操作（2 本指・消しゴム・塗りつぶし・文字・回転・全消去・元に戻す・圧縮）で全消去の後に画素が残らず、元に戻す・やり直すも一致、iOS の予測点が遠く・画面の外・空でも pred に残らない。
- ガラスのぼかしは、描いている間も止めない（R-012、ユーザー: かなりなし。監査では描いている間の GPU の仕事のほとんどがぼかしだったが、見た目を優先した）。
- Delegated Ink Trail は Windows だけで使う。他の OS では API があっても OS が描かない可能性があり、その場合に予測線まで失うため。
- 蛍光ペンの予測は mpred（DEF、既定は 'full'＝ペンと同じ。'need'・'off' も）で決める（T-051・T-052・T-055・T-059。onDown で sPd・sPoly・sNeed を決める。点と点を直線でつなぐ sPoly は 'need' のときだけ）。'need' は needPred: 丸い先端が太さの半分だけ先を覆うので、1 フレーム（fi、tick で測る）後のペン先に届かない分（速さ × fi − 太さの半分、上限 40px）だけ、向きを角速度 om で回して予測する。実機の getPredictedEvents は使わない。蛍光ペンの線は点と点を直線でつなぐ（中点の曲線だと、末尾の直線が次の入力で曲線になるときに引っ込む）。経緯: そのまま描くと外れた予測が目立ち（T-051 で切った）、切るとぬるぬる感がなく、薄く描いても効かなかった（T-052）。`npm run pop` で測ると、消える画素のほぼ全部が予測だった。予測を短くする・減速で弱める・曲がりだけ考える案は、消える画素が残るか先へ伸びる分が減るので採らなかった。その後ユーザーが実機で、濃さ 35% のペンでも同じ症状が出ることを確かめ、半透明（まとめた要素の opacity）が原因らしいと分かった（T-056）。T-056 でかなり解決し、ユーザーが Chrome 標準の予測と差を感じなかったので、T-059 で既定を 'full' に戻した（'need' は開発用で見比べられる形で残した）。
- 半透明の線を canvas の中で濃さにする（T-056、ユーザーの実機の試験: 不透明のペンでは出ない先端のぴょこぴょこが、蛍光ペンと同じ太さ・濃さ 35% のペンで出た）。描いている間に濃さで変わるのはまとめた要素の CSS の opacity だけだったので、それを使わずに不透明の線と同じ経路にした。なぜ opacity で崩れるのかはヘッドレスでは確かめられない（desynchronized の canvas に opacity の祖先があると、低遅延の経路を外れて live と pred が別々のフレームで出るのかもしれない。未確認）。最初は画面大の写し（不透明で線の形を描き、変わった所を live に写す）で作ったが、写しを描き換えるたびにスナップショットの分のコピーが走り、まとめて流すベンチで入力 1 件 9.6 ms（1x）・33 ms（2x）、1 件ずつでも +0.13 ms だったので捨てた（128px のタイルに分けても 1 件 0.2〜0.3 ms）。今の形はキャンバスのコピーがなく、まとめて 12〜15 µs、1 件ずつ +約 20〜30 µs（前の方式は 5〜7 µs・64〜77 µs）。増えた分はほぼ cutPred（T-061 で測った。続いている区間は 1 本の線にして抜く）。新しい区間の所だけ抜いて濃さで重ねる（source-over）案は、区間の縁に薄い輪が出るので lighter にした。前の方式は開発用の「半透明の線の描き方: まとめて」（DEF.blend = 'group'）で残した。サイトごとには覚えない。
- 入力の録画（T-070、ユーザーが「録る機能から始めて」と決めた。T-060 の 1 段目）: 開発用（DEF.dev）のときだけ、その他に「入力を録る（開発用）」（スイッチ。入れると前の録画は消える）と「録った入力を書き出す」を出す。録るのはペン・蛍光ペンの線だけ（予測を測るため）。Chrome の予測点は本体の予測の設定（mpred など）と関係なく、入力ごとに getPredictedEvents をそのまま録る。座標は CSS px、時刻は線の押した時刻からの ms に直して書き出す（小数 3 桁）。上限は 50 万行（約 24 MB。いっぱいになったら録るのをやめてお知らせ）。ページの URL は入れない（ユーザーに送ってもらうため）。インストールページの開発用のスイッチの名前を「開発用の項目をツールの中に出す」にした。
- pointerrawupdate のリスナーは描画中だけ登録する（登録しているだけでコストがかかる）。図形は 1 フレームに 1 回で足りるので使わない。
- 履歴は 128px タイルと外接矩形のうち面積の小さい方で保存する。消しゴムはコピーオンライト。
- 起動直後に warm() で初回コストを前払いする（T-003 以前の計測で初回の確定が 17ms → 2ms、@2x で 60ms → 4ms）。面のタイルは描いた所に作るので前払いできず、初めて描く場所の確定は数 ms 重い。

## 落とし穴

- テストは 1 件ごとに別のブラウザのコンテキストなので、ツールが書く localStorage はテストの間で漏れない（`browser.newPage()` が新しいコンテキストを作る）。
- build.mjs のテンプレートの置き換えは、置き換え後の文字列を必ず関数で渡す。`replaceAll(目印, 文字列)` だと、コードの中の `$&` などが特殊な記号として解釈される。圧縮で変数名が `$` になった T-010（v1.5.0）から T-022（v1.7.0）まで、インストールページのボタンの中身が壊れていた（T-023 で修正）。テストは dist/bookmarklet.txt を使っていたので気づかなかった。今はビルドとテストの両方で、ボタンの href を確かめている。
- 合成した PointerEvent の timeStamp は生成時刻になる。pointerdown より前に作った move は重複として捨てられる（ベンチで一度これにハマった）。
- headless での getImageData の読み戻しは数百 ms かかることがある。時間に依存するテスト（パームリジェクションの 500ms）は、イベントを全部撃ってから検証する。
- headless Chromium は、何も指定しないとソフトウェアで合成する（SwiftShader の GPU 経路でもない。T-111 の監査で分かった）。この状態では desynchronized の canvas の書き出しのたびに canvas 全体を CPU で写すので、合成の重さは実機と比べられない。GPU 経路で測るときは `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist` で起動する（それでも GPU は CPU で動くので、比べるのは相対だけ）。GPU 寄りの処理時間は実機より悲観的に出る。初回だけ遅いのはバッキングの確保が原因（→ warm）。キャンバスの確保は面積に比例して重い。
- ベンチで確定や元に戻すを測る前に、GPU の仕事を吐き出させる（`getImageData(0,0,1,1)` か `api.pixels`）。溜まったままだと、前の処理の分まで次の計測に乗って数倍に見える。@2x は特にばらつきが大きいので、2 回以上流して範囲で書く。
- テストでツールバーの上（画面の上端付近）から描き始めると、pointerdown がツールバーに取られて線が描かれない。継ぎ目の確認で一度「線が消えた」と誤解した。
- 面の画素を確かめるときは、live に残っている線を拾わないように `pixels()`（面だけ）か `screenPixel()`（画面の位置にあるタイル）を使う。確定の直後は live がまだ 2 フレーム残っている。
- この作業環境から *.github.io へはつながらない（ネットワークポリシーで 403）。公開の確認は GitHub API（Actions のジョブ結果）で行う。
- Playwright の mouse で viewport の外（負の座標）からドラッグを始めると、pointerdown がツールに届かない。
- `page.evaluate(CODE)` は CSP を通さずに実行する（Firefox のブックマークレットに相当）。本物の `javascript:` URL として実行するには `location.href = BOOKMARKLET` を使う（CSP のないページでだけ動く）。
- Artifact のビューアはダウンロードをブロックするので、そこでは PNG 保存ボタンが反応しない。
- 取り消し待ちの Ctrl+Z で reopen すると、同じ keydown の途中で onKey が登録される。DOM は配送中に足されたリスナーを呼ばないので、絵の undo までは進まない（テストで確かめている）。順序を変えるときは注意。
- 選択の動作確認で「動かしたのに位置が変わらない」ときは、まずつまみに当たっていないかを疑う（細い枠では辺の中央のつまみが中身に重なる）。テストでは `.sel b`（外枠）の矩形からつまみの位置を求める。
- `pixels()` には文字の物も入る。線の有無を画素で調べるテストでは、文字と重ならない範囲を見る（文字が動いて測る帯に入り、一度落とした）。
- ショートカットは keydown だけを止めている。keyup はページに届く（テストでページへのキーの漏れを数えるときは、ショートカットを押した後に数え直す）。
- テストの `toolOn()` は DOM の順で最初の `.b.on` を返す。図形はバーの shapeB がパネル内のボタンより先にあるので、shapeB の title（今の図形の名前で始まる）が返る。閉じたパネルの中のボタンも `element.click()` なら押せる（`[title^="PNG"]` など）。見えているかも確かめたいときは `mouseClick()` を使う。
- 起動直後や fit() の後は、暖機（warm）が setTimeout で遅れて動く。すぐに destroy すると 0 の大きさのキャンバスを drawImage してページのエラーになる（手元では間に合って通り、CI でだけ落ちていた。T-032）。destroy で warmT と rz を止めている。遅れて動く処理を足すときは、destroy で止める
- シャドウ DOM の CSS のクラス名は短く、`.g`（live のグループ）・`.p`（入力の板）・`.s`・`.t` などが全体に効く。新しい部品に同じ名前を付けると、position:absolute などが当たって崩れる（T-007 で一覧の行に `.g` を使って重なった）。足す前に CSS を grep する。
- backdrop-filter は、要素の大きさだけを元にぼかす。細長い要素（高さ 40〜60px）では下の文字がほぼくっきり残る（headless の Chromium で確かめた。ツールと関係のない素のページでも同じ）。周りも拾うには、要素を広げて mask で切る（T-041 のガウス方式）。外側で overflow・clip-path を使うと効かない。
- 画素のループの速さは、ヘッドレスでも実機と同じ（CPU）。測るときは単独で何度も回した値ではなく、本物の操作の初回（冷えた状態）で測る。単独で測った塗りつぶしの走査が速く見えたのは、たまたま囲まれた小さな領域だったため（T-047 で一度取り違えた）。2x の塗りつぶしの合計は、ヘッドレスでは GPU の読み戻しとコピーが大半で、±20 ms ぶれる。
- 筆・鉛筆の太さを本物の時間の線で見るテスト（ペンの種類）は、全部のテストを流すと負荷で 1 回だけ落ちたことがある（T-115。単独で 3 回・全体の流し直しで通った。予測は確定した線に関係しない）。
- `fresh()` は dist/bookmarklet.txt から起動する。前の版でテストが落ちるかを確かめるときは、dist/paint.min.js と bookmarklet.txt の両方を差し替える（paint.min.js だけ替えて、前の版でも通ると一度取り違えた。T-055）。
- 合成の PointerEvent の timeStamp は、`Object.defineProperty(e, 'timeStamp', { value })` で決められる（予測・速度のテストで、計測にかかる時間で速さが狂わない）。
- 同じ canvas に 2 回以上 getImageData すると、Chrome はページのコンソールに「Canvas2D: Multiple readback operations…」の警告を出す（T-114 で確かめた）。読み出しを足すときは、1 回で読むか、読み出し用の別の canvas に写してから読む（テストで警告が出ないことを見ている）。
- Chrome の Paint はページ全体の記録なので、ツールの中の DOM を変える（パネルの display・ボタンの disabled・お知らせの文字など）と、変えたのがツールの中だけでも、重いページでは 1 回 5〜8 ms かかる（T-119 で測った。ホストに will-change: transform・contain: strict、パネルに contain を付けても減らない）。描いている間・押した瞬間に DOM を変える物を足すときは、opacity・transform（will-change 付き）で済ませる。パネルを閉じる（色を選んだ後の次の線の押した瞬間）は、この 5〜8 ms が残っている（opacity で隠す形にすると、隠れたパネルのボタンに Tab で届く・ガラスのぼかしが隠れても残るかもしれない、ので見送った）。
- `npm run bench` は 3,000 点を 1 タスクで一気に流すので、入力の時刻がほぼ同じになる。canvas の書き出し（Blink の FinalizeFrame → DispatchFrame。描いた canvas ごとに、タスクの終わりに 1 回）もまとめて 1 回になり、入力ごとの本当の重さが見えない。入力ごとの重さは、CDP の Input.dispatchMouseEvent を決まった間隔（125〜1000 Hz）で送って測る（T-111 の監査の scratchpad/audit/rate.mjs）。自前の予測は輪の 64 点を毎回全部たどり、予測もいつも上限まで伸びるので、入力 1 件の時間が悲観的に出る（T-060 の前より 1x で約 +3 µs）。入力の時刻を 1 ms・4 ms 刻みにすると差は +0.3〜0.8 µs（scratchpad の ppbench.mjs で測った。リポジトリには入れていない）。
- テストで isMobile: true にすると、viewport の指定がないページ（/long など）は 980px 幅のレイアウトになり、live / pred が大きくなって canvasPix も上限（hcap）も変わる（T-120 で、圧縮が始まらずに一度落とした）。メモリと圧縮のテストは isMobile なし（タッチが要るなら hasTouch だけ）で作る。
- ヘッドレスで重い状態を作るとき: Playwright の `page.mouse.move` は処理されるのを待つので、ページを止めるとマウスも止まる（本物と違う）。CDP の `Input.dispatchMouseEvent` を待たずに送り、`timestamp`（秒）に生成した時刻を入れる。ページのメインスレッドを止めるだけでは、まとめて届く点の最後が新しいので予測線はほとんど消えない。ブラウザごと遅れる状態は、Node 側で点をためて、元の時刻のまま 15〜75 ms ごとにまとめて送って作る（scratchpad の load/jankrec3.mjs）。
- `npm run pop` の合成の入力は、座標が整数で時刻を ±1.5 ms ぶらしてあるので、ゆっくりの弧では自前の予測の長さが揺れ、消える画素が前（直線の外挿）より多く出る（150 px/s で 3.9 → 10.0。速い円では 37.8 → 14.2）。人の録画では消える長さが減っているので、録画の方を信じる。合成の PointerEvent の getPredictedEvents は空なので、ヘッドレスで ppred = 'chrome' にすると自前の予測（ownPred）になる（T-116 の前は 12 ms の直線の外挿）。予測の付いた入力は `new PointerEvent('pointermove', { predictedEvents: [...] })` で作れる（localhost など安全なページで。data: のページでは getCoalescedEvents がない）。CDP の Input.dispatchMouseEvent なら Chrome 自身の予測が付く。
- CDP の Input.dispatchTouchEvent では、指を離した合図だけを落とすことはできない（touchEnd を送らないと次の touchStart で前の指が残る）。線の終わりを取りこぼした状態は、pad に合成の PointerEvent の pointerdown・pointermove だけを送って作る（test/audit.test.mjs の T-118 のテスト）。
- テストで「ページの上にツールがかぶっていない」を見るときは、elementFromPoint が `PAINT-BOOKMARKLET` かどうかで判定する（下にあるのは本文の段落など、場所で変わる）。

- ヘッドレスの Chromium でも、CDP の `Input.synthesizePinchGesture`（isMobile と viewport の meta）で拡大できる（T-136）。座標は見えている範囲の CSS px で、拡大した後に元の大きさの座標を渡すと「Position out of bounds」で落ちる（T-138 で一度、時々だけ落とした）。合成の PointerEvent は view を渡さないと pageX にスクロールが入らない（pageX = clientX）。
